# Kestrel architecture

This document describes the system as implemented today: its components, data flows and trust boundaries. The intended evolution, including The Nest's per-user VMs and saved evidence, is described separately in [goal-state.md](goal-state.md). A goal or proposal there is not a claim that it is already implemented. See [resilience.md](resilience.md) for outage boundaries, [box.md](box.md) for box operations and sandbox details, and [byo-box.md](byo-box.md) for bringing your own box.

## System overview

Kestrel has an interface for interacting with agents and viewing their desktops, and boxes that run the work. A box may be operated by Kestrel or supplied by a user. The control plane signs users in, coordinates access to boxes and handles shared services. Today Kestrel-operated managed boxes can serve multiple users; the goal is a separate Nest VM per user on a shared host.

## Components

| Component | Responsibility | Location |
|---|---|---|
| Web interface | Public pages, authenticated workspace, thread and desktop views | `packages/app` |
| Mobile interface | Multi-box thread lists and box-scoped thread and desktop access | `packages/mobile` |
| Shared composer | GitHub reference format, draft parsing and the DOM editor used by desktop, phone web and Expo native WebViews | `packages/composer` |
| Shared UI | Theme tokens, primitives, the chat transcript and panels (quotas) rendered by desktop, phone web and Expo native WebViews | `packages/ui` |
| Control plane | GitHub OAuth, sessions, box registration and tokens, credentials, automations, PR watches and relay | `packages/control` |
| Hub | Durable control-plane state and coordination, including fleet registry and scheduled events | `packages/control/src/hub.ts` |
| Box | Thread API, agent runs, workspaces, sandbox, desktop and tools | `packages/server` |
| Host experiment | Local per-user CPU VM lifecycle CLI; not yet the Nest host agent | `packages/host` |
| Shared protocol | Schemas and types for APIs, events, relay and domain objects | `packages/protocol` |

Phone browsers use the mobile app's web export. Its reference composer and the desktop composer share one DOM
implementation; Expo bundles that surface locally for native iOS/Android through `use dom`. References serialize
as ordinary GitHub Markdown links with explicit repository, kind and number, so drafts and messages cross UI
surfaces without a protocol change. See [mobile references](../packages/mobile/README.md#github-references).

Chat box availability is shown by the box activity indicator, not a global offline banner or sidebar connectivity
alert. Losing the live connection warns only while an agent turn is running; idle reconnects stay quiet. Failed
prompt submissions still show an error beside the composer and keep the draft available to retry. Desktop send
errors use the same frosted-glass warning style as the floating banners.
Reconnecting refreshes the thread, messages and runs; fresh snapshots replace stale pre-disconnect state while
preserving live events that arrive during the refresh.
Relay connectivity failures carry the `BoxOffline` error tag; an application's 502/503/504 alone is not evidence
that its box is down. Query-error selection preserves actionable failures even when another query is unreachable.
If an essential initial snapshot fails with no cached data, the conversation shows an inline load-failure state
instead of an empty transcript or a recurring offline banner.
For relayed mobile boxes, failed health requests leave availability unknown; only a successful box-status response
declares the relay offline. New-thread sends attempt the request when availability is unknown and report its error.

In desktop Settings, Profile manages GitHub repository access, including connecting and reconnecting OAuth.
The repository picker sends users without a GitHub connection to Profile to set up that access.
Connections contains only model access: **Harnesses/Subscriptions** groups subscription sign-ins and installed
harnesses, with each harness's model-visibility picker beside its name; **API keys** keeps key-based access and
its model preferences together. A provider's picker lists each model once; enabling it enables that model under every
harness it supports, so the same choice appears in each compatible harness tab of the chat picker. These pickers
change which models appear in chat. **Refresh models** reads the selected box's authenticated runtime catalog
(`GET /api/models?refresh=1`); clients also poll hourly. See [model coverage](harnesses.md#third-party-model-coverage)
for provider/CLI discovery, fallback behavior and curated compatibility metadata.
When no key rows are visible, API keys shows a centered “No api keys added” empty state.
Subscription rows support multiple isolated accounts per provider: **+** repeats sign-in, the signed-in identity
menu switches the account for subsequent runs and quota reads, and **Disconnect** lists accounts to remove.
The status pill shows **N connected** only above one account. Existing runs keep their original login; switching
does not copy credentials or native sessions between account homes. See [credentials and sessions](harnesses.md#credentials-and-sessions).

Settings › Threads (`/settings/threads`) groups thread preferences into sections. Its Text generation section stores
each user's choices on the active box (`GET`/`PUT /api/settings/text-generation`). The section's toggle disables its
controls without clearing the selected model, thinking level, title instructions or streaming choice. Off skips
title-generation requests, leaves new threads' original prompt-derived titles intact and restores token-by-token
responses for new runs. A pending generated title is not applied while the section is off. Re-enabling restores the
saved choices; it does not rename existing threads retroactively.

The right-aligned model and thinking controls are shared with the composer, with no model-reset action. “Conversation
model” inherits that conversation's model and thinking level; an explicitly selected model uses its own supported
default until a level is selected. Custom thread-title instructions are appended to the title prompt. While enabled,
response streaming either reveals completed paragraphs and fenced code blocks or waits for the assistant's full
response; tools and thinking remain live.

New desktop and mobile threads opt into automatic naming with `CreateTaskBody.generateTitle`. When enabled, the first
accepted user message starts a separate, non-resuming text-generation request in a temporary sandbox workspace, using the
owner's existing provider credentials without the thread's MCP tools. It never enters the conversation history or
changes its model/session. The provisional prompt-derived title remains on failure; generated titles cannot overwrite
an archived, deleted or renamed thread. Explicitly named automations and delegated threads keep their titles.
The settings and initial-title flow are inspired by [T3 Code](https://github.com/pingdotgg/t3code); Kestrel uses its own
prompt, provider integration and UI components.

The shared composer also owns the app-command catalog and invocation rules (`src/commands.ts`). App actions such
as `/usage` execute locally on suggestion selection or message submission; they never reach the harness and
override same-named slash commands, but not `$skills`. Each host implements the exhaustive `AppCommandHandlers`
map, so adding an action requires both desktop and mobile behavior. Desktop opens its Quotas dialog; mobile
pushes the existing Quotas screen only after a live DOM snapshot's unconsumed draft is durably saved. Native
menu picks request that snapshot over the fire-and-forget bridge. Ordinary Send reads live content without
locking or blurring; a typed app command hands off to the same locked snapshot path as a menu pick. The DOM
locks editing synchronously before capture and keeps successful app actions locked until their editor unmounts;
rejected actions and failed saves unlock. Pending storage and navigation therefore cannot discard visible edits.
Mobile draft storage serializes reads and writes per key across composer mounts, including pending SecureStore
operations.

Typing `@` at a word boundary in the desktop or phone composer opens model suggestions in the command-menu style.
Suggestions use the same connected, visible models as the model picker, search names and routing identities, and
show the harness logo with a provider-qualified slug identifying whose connection/usage the model uses. Selecting
one inserts an atomic logo/name chip; it does not change the answering model or automatically launch a child.
Inline mentions use a smaller 12px logo and a subtle rounded backing in both the composer and sent transcript.
The prompt and saved draft retain a readable Markdown mention with the exact model id, provider and harness, so
the agent can use that identity with `delegate_task` or `delegate_batch`. Model and GitHub-reference chips can
coexist; both are masked from autocomplete triggers. Shared parsing and provider-to-harness identity live in
`packages/composer/src/models.ts`; the native editor bridge uses the same insertion and persistence contract.
The shared user transcript renders those mentions as logo/name chips too, while keeping ordinary or malformed
mention text literal. An empty model-suggestion list does not own Enter or Tab: desktop Enter submits the message,
and phone Enter retains its normal newline behavior; the phone's Send button submits as usual.

Shared panels follow the same pattern: `packages/ui` holds the DOM component with plain JSON props, each app
fetches the data with its own client, and the phone app renders the component through a `use dom` wrapper whose
Tailwind comes from `@cloudagents/ui/dom.css` (Metro runs `@tailwindcss/postcss`). See
[shared desktop components](../packages/mobile/README.md#shared-desktop-components). The chat transcript is one such
component: the phone app keeps the thread in its query cache and sends the DOM side a snapshot, then only what changed.

## Access and communication

The Worker serves the web app and public site, handles sign-in, and issues box-scoped tokens. Direct clients use each box's URL; the box verifies its token offline. The web app can send eligible API calls over a WebRTC data channel after signaling directly to the box, with HTTP fallback; mobile, events, uploads and previews use their existing HTTP or WebSocket paths. Desktop video, audio and input use WebRTC only, signaled over the desktop WebSocket (direct, or through the legacy relay); there is no WebSocket media fallback. Both apps list threads across boxes and route a thread's requests to its box. See [byo-box.md](byo-box.md) for connection setup and direct-path limits.

The Hub also maintains a legacy WebSocket relay for users without a managed box. In that path the box dials out and the control plane forwards requests, event streams and desktop signaling and status. Desktop media never passes through the Hub: WebRTC connects directly or through a TURN provider. When the Worker has Cloudflare Realtime TURN configured, registered boxes authenticate `POST /box/turn` with their existing identity and add expiring provider credentials to viewer ICE configuration and to their own peer automatically, unless local TURN is explicitly configured. Both ends then allocate a relay, so neither needs a candidate the other can reach. The provider API token stays in the Worker. See [TURN operation and rollout](box.md#webrtc-desktop). This is a current deployment path, not the goal for low-cost BYOB. The [goal state](goal-state.md#control-plane) describes the planned cutover and direct connectivity work.

Managed boxes are registered in the Hub and can serve multiple users. Users are assigned to an active or draining box, and new assignments favor the active box with the fewest users. BYOB boxes have a single owner. On either path, the box enforces thread ownership using the identity supplied by the relay or a verified box token. The control plane and box have different responsibilities: signing in does not itself authorize access to another user's thread.

The authenticated `GET /api/capabilities` reports a versioned snapshot of platform, sandbox level and desktop prerequisites; it does not guarantee that a desktop will start. Older boxes return 404. This is an initial capability probe, not yet the full goal-state contract.

## Agent execution and data

Upload requests may carry an `operationId` UUID. Retrying the same bytes, MIME type and sanitized name for the same
owner and thread returns the original attachment, including after it has been attached to a message. Reusing the key
with different content is rejected. The record lasts for the lifetime of the pending upload or its message, until the
thread is deleted. The web client keeps the key in memory while retrying a file; a page reload starts a new operation.

A thread has a workspace, messages and runs. Repositories are checked out on demand, each on a thread branch. The box maintains per-user repository mirrors, fetching with the user's GitHub credentials on the host. Host-side Git operations use a separate shadow repository so agent-writable repository configuration cannot direct host commands. Thread data, workspaces and mirrors live on the box.

Every agent-controlled task launch (agent CLI, `workspace_exec`, desktop terminal and launched apps) receives
`GIT_AUTHOR_NAME` / `GIT_COMMITTER_NAME` set to the thread owner's GitHub login and both email variables set to
`<id>+<login>@users.noreply.github.com` by default. Older accounts can still use GitHub's legacy
`<login>@users.noreply.github.com`; their owner must select that format through the box's
`CLOUDAGENTS_GIT_LEGACY_NOREPLY_USERS` setting (see [commit identity](box.md#git-commit-identity)).
The public profile API does not expose this privacy setting, so Kestrel does not infer it from account age.
The host resolves the numeric ID and canonical login through GitHub's `GET /users/:login`, validates the response
against the thread owner and reuses successful lookups for the box process's lifetime. The owner's connected
token authenticates that lookup when available; a 401 or 403 response is retried once without the token because
profiles are public. If identity resolution still fails, the launch is blocked rather than guessing an account.
Dev-login sessions instead use `<login>@kestrel.invalid`, never an unrelated real GitHub identity. Background
automation and activity dispatches preserve this dev identity for the configured `DEV_SESSION_LOGIN` on both
the legacy relay and managed-box token paths, even though they have no browser session.
This gives fresh task homes a usable identity and takes precedence over stale identities in persisted home or
checkout Git config. GitHub credentials authenticate a push; they do not set the author of the commits being
pushed. Explicit Git authorship (for example `git commit --author` or a cherry-pick) still preserves the original
contributor. Commit-message co-author trailers are not rewritten, and existing commits are not repaired by this
setting.

The harness starts the CLI selected by the model's catalog route. API access and harness identity are independent:
compatible API-key models can run in Claude Code, Codex or OpenCode without changing the credential provider.
Subscription logins remain native-only. The broker forwards the harness's supported upstream protocol and keeps
real API keys on the host; it does not translate unsupported APIs. See [harness compatibility](harnesses.md#harness-compatibility).
The box supports steering and interruption while a run is active. Native sessions are isolated by provider and
harness; returning to one carries only messages from runs since that session last participated. Without a usable
session, the run starts fresh with bounded conversation history. Prompts travel on stdin, and raw CLI diagnostics
never become portable conversation history. Catalog routes and validated provider-qualified runtime identities
live in `packages/protocol`; discovery results remain scoped to the signed-in user and selected box.

Every harness uses one compact completed-run disclosure in the shared desktop/phone transcript, inspired by
[T3 Code's timing presentation](https://github.com/pingdotgg/t3code/blob/main/apps/web/src/components/chat/MessagesTimeline.logic.ts).
Its “Worked for …” duration uses Kestrel's persisted `Run.startedAt` and `endedAt`, not provider-reported
response or turn durations. This wall-clock span includes queueing, startup, tools and waiting. Durations use
milliseconds below one second, tenths below ten seconds, then seconds/minutes/hours, rounding before choosing
the unit. Failed and stopped runs retain their status and measured elapsed time. Restart-reconciled runs show
“Interrupted by restart” without counting downtime as work; missing or invalid boundaries never invent a duration.
The completion clock stays on the collapsed row. Steering splits the content but not the run summary.
The row keeps its muted color and uses the thinking block's trailing 14px caret: revealed on hover or keyboard
focus, rotated down and kept visible while open.
Saved replies without loaded transcript items keep the summary after their answer.

Expanding the disclosure lists input, output and cached tokens plus average output tokens per second over the
same wall-clock span. The collapsed row already carries elapsed time, so the details do not repeat it. Input
excludes cache reads, which appear as cached tokens separately; cache writes count as input. Input and cached
tokens come from main-agent response usage, never added to turn aggregates, so they are not double-counted;
subagent rows are excluded. Output remains the completed turn aggregate. ACP harnesses (OpenCode, Antigravity,
Devin) report usage only per turn, already split into input and cache buckets, so the transcript emits that split
as the turn's one usage item; a bucket an agent omits next to a reported input counts as zero (OpenCode omits zero
buckets). A harness that reports only a cache-inclusive turn aggregate still contributes its output, but its
cache-free input cannot be recovered, so input and cached tokens say “Not reported” instead of guessing. This average
includes tools and waiting; it is not model-generation speed. Incomplete, failed or stopped invocations do not
present partial token totals as complete; unreported values say “Not reported” rather than showing `? tok/s`.
Counts are compact with exact values on hover. Per-response metadata remains stored but no longer creates rows
or splits consecutive tool groups. The context meter remains a separate current-context measurement.

OMP, Pi and Hermes remain outside the current product scope. Existing harnesses share compatible API-key
providers through the model picker rather than introducing a separate per-thread harness control.

At startup, historical runs from the retired harnesses retain their tasks, messages and run records, but lose
obsolete provider/model/harness routing metadata; their unusable resume targets are discarded before state
validation. The migration is written atomically only after the remaining state validates, so unrelated corruption
still rejects startup without overwriting the file. New requests continue to reject the retired identifiers.
Claude Code session records carry the actual model provider, including third-party gateways, so switching to
Anthropic cannot resume a gateway session and returning to that gateway can resume its own.
The Hub also resets the six retired model selections in saved automations to `null` (the box default), preserving
their prompts, schedules, GitHub triggers and enabled state. Model pickers exclude a connected account when it
explicitly reports unavailable; another usable connection for the same provider can still offer its models.

The desktop and mobile composers' thinking controls open a stepped slider in Kestrel's monochrome theme, with a flat track and a trigger ring that fills by level: Low 25%, Medium 50%, High 75%, Extra high 87.5%, Max 100%; Off leaves it empty. They offer only the selected model's supported effort levels, ordered lowest first, with `none` labeled Off. There is no Default stop: an absent or unsupported saved level selects and sends the model's catalogued default effort, or its lowest supported effort when no default is specified (Off where supported, otherwise Low). Z.ai models default to Max, preserving the provider's default reasoning depth. With no model or no effort support, the control is hidden and effort is unspecified. The choice survives thread changes and reloads. Desktop uses a popover; mobile web and Expo share a touch-sized bottom sheet. The web sliders use native range inputs for pointer/touch input, arrow keys, Home and End; Expo uses React Native touch responders and screen-reader increment/decrement actions.

The desktop chat composer keeps the last 100 accepted, non-empty prompt texts in this browser's local storage,
shared across threads and retained after reload. Up recalls older prompts at the start of the text, or at the
end only when the draft fits on one visual line (no newline or soft wrapping). Once browsing history, Up at
the end of an unchanged recalled prompt continues to older entries, even if that prompt spans multiple lines.
Down recalls newer prompts at the end, then restores the unsent draft. Editing a recalled prompt makes it the
new draft. History includes only typed text, not attachments, picked answers or generated element context;
failed sends and the local `/usage` command are not recorded. Autocomplete menus, question options, text
selections, modified arrow keys and IME composition keep their existing keyboard behavior.

Agents normally run in a per-thread bubblewrap sandbox and systemd scope. The `strict`, `basic` and `off` modes provide different isolation; in particular, `basic` shares the host network. MCP provides the agent's box tools. Model requests go through the broker using a per-run token, so the sandbox does not receive the real model key. Host-side GitHub tools likewise use credentials outside the sandbox. See [box.md](box.md#agent-sandbox) for the actual sandbox guarantees and limitations.

MCP, the credential broker and `/gh/` use a separate loopback-only listener rather than the public box listener. Strict task networks forward that listener into the task namespace; basic and off share the host network. Per-run credentials still gate those routes.

## Desktop, preview and evidence

The box manages a desktop for a thread, captures its display and accepts input. The desktop streams over WebRTC only: H.264 video and Opus audio on recvonly transceivers, and input on data channels, sent directly from the box to each viewer. The desktop WebSocket carries its status and the WebRTC signaling, directly or through the legacy relay. Kestrel relays no media; the default STUN server only lets peers learn their public addresses, TURN is used when the box operator configures it, and registered boxes add managed provider TURN to both ends automatically. Touch devices get a touch control layer. The mobile app shows the viewer through the `/embed/desktop` page, in a WebView (an iframe on the web). Capture is damage-driven and the encoder stops shortly after the last viewer leaves. A preview exposes an agent-started web service through a scoped preview session. Desktop and preview isolation depend on the box's sandbox mode.

Screenshots produced by agent tools can be retained and shown in the transcript. Files in a workspace can be downloaded. Saved video clips, marked output files and evidence summaries are proposed in [goal-state.md](goal-state.md#saved-evidence); they are not yet the evidence system described there. A capture attached to a pull request is committed to its repository, so on a public repository anything visible on screen becomes public. The shared `kestrel-evidence` branch is kept after the pull request closes. Deleting it removes the image from the branch and the comment's link; the commit and blob remain in the repository's object store until garbage collection and may remain reachable by commit SHA or from forks. Live streaming supports both observing work in progress and reviewing the desktop interactively.

## Automations and PR watches

The control plane stores scheduled and GitHub-triggered automations, verifies webhook deliveries and dispatches work to a box. An automation starts a thread and sends its prompt, optionally with a repository and PR context. PR watches use the shared GitHub webhook to wake a thread when relevant review, comment or completed-check activity arrives. The agent must inspect the current PR state; a webhook payload is not an instruction.

A thread can follow any number of pull requests with `github_pr_watch` and stop following one with `github_pr_unwatch` (`repo` + `number`), or all of them without arguments. Watching adds the pull request to the thread's `Task.pullRequests` registry, which is what the app shows; a watch is stored in the control plane by thread, repository and number. The control plane accepts a watch when the owner's GitHub token can see the pull request and the thread exists and is not archived; the box records it in the registry only after that, so a refused watch leaves no entry. The owner must be able to administer each repository's webhook. The control plane verifies and deduplicates deliveries, coalesces notifications per pull request in a persistent queue, and retries delivery to the box without polling. Archiving or deleting the thread removes its watches on the next delivery; closing a PR stops that watch, and any watch the control plane drops is cleared on the box.

Automations and watches currently use managed or legacy boxes, not user-owned boxes. The goal is parity across box types; see [goal-state.md](goal-state.md#the-box-contract).

## Operational boundaries

- **User and thread isolation:** the box checks ownership on thread data and operations. Current managed boxes are shared between users; a per-user Nest VM is a planned boundary, not a property of today's fleet.
- **Agent isolation:** sandbox strength depends on mode. Run-scoped MCP and broker credentials expire when the run ends. A sandbox is not a substitute for the box's authorization checks.
- **Credentials:** the control plane stores connection secrets; the box retrieves credentials through its authenticated path. Model keys and GitHub tokens are used outside the agent sandbox.
- **Availability:** box-local threads, files and direct streams depend on the box being reachable. The control plane's registry and sign-in do not make an offline box available.
- **Shared changes:** `packages/protocol` is used throughout the system. Coordinate changes to shared schemas and account for compatibility across deployed clients and boxes.

## Direction and outstanding work

The product direction is a common box contract and capabilities across BYOB and The Nest, direct low-cost BYOB connections, cross-platform support through Linux, WSL and Lima, saved visual evidence, and per-user Nest VMs with different resource shapes and usage-based billing. These are goals with implementation and validation work remaining, not present-day guarantees. The architecture, dependencies and open decisions are in [goal-state.md](goal-state.md).

### Nest: current and planned

**Current:** `packages/host` provides a local CPU-VM lifecycle CLI and a QEMU launcher. The non-billable meter collects host-side process and disk samples, ingests records into the control plane, and reports estimates and coverage gaps. These are experiments, not an integrated managed fleet or charging system. See [packages/host/README.md](../packages/host/README.md) and [scripts/nest-meter/README.md](../scripts/nest-meter/README.md).

**Planned:** a host agent and control-plane placement for per-user VMs; CPU and GPU shapes; suspend and wake on activity; parking persistent volumes for later resumption; and reconciled, usage-based billing. Cloud Hypervisor is a candidate, not a completed runtime choice. The detailed design and its constraints remain in [goal-state.md](goal-state.md#the-nest).

## Implementation details

- One Worker serves the control API and the web app on `app.kestrel-agent.com`; `kestrel-agent.com` (and `www.`) serves public pages and sends other paths to the app host. On the app host, phone browsers get the mobile web export (`packages/mobile`, built into `dist/m`) on the same URLs instead of the SPA ([details](../packages/mobile/README.md#on-the-web-phones)). Clients also connect directly to boxes where available.
- The Hub Durable Object relays app requests to a box over the WebSocket the box dials out to. That is the legacy relay, used by users with no managed box, so nothing on that box is exposed to the internet. Durable Object requests are the scarce resource (100k/day on the free plan; every RPC, every relayed request and every 20 incoming WebSocket messages count as one), so the relay is kept lean: a browser API call costs one Hub request (the Worker forwards the session id and the Hub resolves it, attaches credentials and relays in that request), and what changes often is pushed over WebSockets instead of polled, since the Hub's outgoing messages are free. The thread list comes over `/api/events` (`task.updated` for every thread of the user, `task.deleted`), the Desktop graphs over `/api/tasks/:id/stats/stream`, and the diff is refetched on agent activity rather than every few seconds. The desktop WebSocket, which carries status and WebRTC signaling, is opened only while the desktop is starting or running (the box refuses it otherwise, and retrying would cost a request every 2 s). Desktop media never passes through the Hub. A `<img>` in a WebView cannot send the session cookie, so `POST /api/file-token` mints a `FileToken` that the Worker accepts as `?access_token=` on GETs of the three box file paths (`Paths.taskAttachment`, `Paths.taskRunImage`, `Paths.taskCheckoutIcon`); it is bound to the session that minted it (relayed with that session's user and dev flag, revoked when it signs out or expires), lives at most an hour, is refused on every other path and method, and is stripped before the file is relayed. It is a bearer credential in a URL, so it can reach browser history and logs, and a file opened in the system browser carries it; that is the accepted cost of images in a WebView. The mobile desktop viewer's WebSocket has the same problem and a stronger capability, so it gets its own token: `POST /api/tasks/:id/desktop/token` mints one accepted as `?access_token=` on that task's desktop stream only. It lasts five minutes, is bound to the minting session in the same way, and neither kind of token works in the other's place.
- The control plane signs users in; the box decides what they can see. Each thread is owned by the user who started it, and the box serves a thread and its runs, diffs and desktop only to that user (identity comes from the relay, or on a user's own box from a box token; otherwise the box's own port has no user and gets no thread data).
- Web and mobile thread lists show a repository identity per thread (after t3code's project favicons), including the web's collapsed rail and both archived-thread views. The shared `threadIdentity` helper keys it on the thread's first checkout: that repository's own icon when it has one, else initials of the repository name, with the finish hashed from the repository, so every thread on a repo looks the same. A thread without a checkout takes initials from its title and its finish from its ID, so a rename changes the letters but not the finish. Initials come from the first two words (or the first two letters of a single word), skip punctuation and emoji, and fall back to `KT`. Finishes are eight two-hue glass tints (`THREAD_TINTS`: cool hues plus graphite, leaving green, amber and red to status); a loaded icon sits on the graphite one. Expanded sidebar rows centre each avatar against the title and status lines, independently of repository chips below them. The status icon sits immediately before matching-colour status text, with timestamps kept muted. Only the collapsed web rail keeps an overlaid status badge, on a soft backing that fades out toward its edge.
- The box finds a repository icon once, when it makes the checkout, in the owner's mirror at the fork commit (never in the agent-writable checkout): the first regular file (not a symlink) among well-known favicon/icon paths, else the `<link rel="icon">` an index page or root route names, if it is a renderable image of at most 256 KB. `Checkout.icon` records its path and blob id; `Paths.taskCheckoutIcon` serves only that blob, from the mirror, with `Content-Security-Policy: sandbox` and an immutable cache, so a browser fetches each icon once rather than costing a relayed Hub request per render. Checkouts made before this have no icon and show initials.
- A user can run and select their own box (Settings › Boxes; [byo-box.md](byo-box.md)). - A thread starts in an empty workspace directory with no repository. The agent checks repositories out on demand with the `repo_checkout` MCP tool (a GitHub `owner/name` the owner's token can read, or a public `https://` URL; never local paths), at most one checkout per repository, each on its own thread branch. - Automations are user-defined triggers that start a thread on the owner's box: a cron schedule in an IANA time zone, or a GitHub `pull_request` event (opened, reopened, ready for review, synchronize, review requested). The Hub stores them, arms one alarm for the next schedule fire, and receives GitHub deliveries at `/webhooks/github` (verified with a per-repo HMAC secret; deduped by delivery id). An automation names an optional GitHub repository (required for `pull_request` triggers). Each repo has one webhook shared by its automations, created on GitHub with the owner's token when the first enabled GitHub automation is saved; the Hub change is saved first, and the webhook is removed when the last enabled GitHub automation on the repo is deleted, disabled, or switched to a schedule. Removal is best-effort and needs the owner's token; without one the webhook stays and is reused later. Firing starts a thread on the box (`POST /api/tasks`) with the automation's repository checked out; a PR run also passes `pullRequest` and the PR's base branch, so the checkout forks from the PR head and its diff shows only the agent's edits. Then the automation's prompt is sent.

- Under the desktop stream, the Desktop tab graphs the thread's own resources over the last minute against its limits (pushed over `/api/tasks/:id/stats/stream`, one sample a second; owner only): RAM and CPU from the thread's systemd slice (`memory.current` and `cpu.stat`, against the thread's ceiling: its own `MemoryMax` and `CPUQuota` under `per-thread` provisioning, the box's totals otherwise; empty without systemd), storage against the per-thread storage limit, and VRAM for the whole GPU, labelled shared, since there is no per-thread VRAM limit. Hovering a graph shows the polled sample nearest the pointer. The box samples a thread (`stats.ts`) only while a stats stream is open, and keeps its history 15 s after the last one closes. Storage (workspace, home, shadow repos and the thread's attachment files, pending uploads included) is measured for every thread every 30 s, uploads count as they arrive, and the box enforces the limit (`core/storage.ts`; see the limits table in [box.md](box.md#resource-limits)).
- The panel under the desktop has two tabs: Resources (the graphs above) and Applications, what each program in the thread uses now (`app-usage.ts`, read with the same sample). It takes every process in the thread's slice (`cgroup.procs` of the slice and its scopes) and groups them by program name from argv; a script run by node, bun, deno or python is named after the script's package or file (`node · vite`, `node · typescript`). Each group shows its process count, its memory against the thread's RAM limit and its CPU (`utime` + `stime` since the previous sample) against the thread's quota. Memory is proportional (`Pss_Anon` + `Pss_Shmem` from `/proc/<pid>/smaps_rollup`): a page several processes share, such as a fork's copy-on-write pages, is divided between them, so no page counts twice. A process that made itself non-dumpable (pasta) hides its `smaps_rollup` from the box, so its resident memory from `status` stands in. The eight largest groups are named and the rest summed as Other. The slice's `memory.stat` gives the last rows: Page cache (`file` minus `shmem`), tmpfs & shared memory (`shmem` minus what processes map, e.g. files in the sandbox's `/tmp`) and Kernel (`memory.current` minus `anon` and `file`), so the rows add up to the RAM graph's reading, give or take what changed between the reads. Boxes older than this send no list, and the tab says so.

HTTP assets and text HMR WebSockets use the existing box relay, and the box connects only to `127.0.0.1:<registered port>` from the task's private network namespace. No dev-server port is published on the host or internet. “Select element” highlights a DOM element and returns its label and CSS selector for copying into a message. This sandbox intentionally does not expose app-origin storage, cookies, popups, or service workers.
- Users attach files by uploading them first (`POST /api/tasks/:id/uploads`, raw bytes, `Content-Type` as the file type, optional `?name=`; at most 10 MiB). - The thread sidebar's pull-request tab (the PR button in the thread header and collapsed rail) shows every pull request the thread owns or manages, with GitHub's live view: state, checks, review decision, diff size and branches. Opening one shows a summary (description, labels, reviewers, checks, comments), the activity timeline (opened, commits, comments and reviews, merged or closed) and the pull request's own diff, and can comment, review (comment, approve, request changes), merge, close or reopen it, and toggle the thread's watch. The box serves `GET /api/tasks/:id/pull-requests`, `GET /api/tasks/:id/pull-request?repo=&number=`, `GET /api/tasks/:id/pull-request/diff?repo=&number=` and `POST /api/tasks/:id/pull-request/action` (all owner only, all limited to the thread's registry); GitHub tokens stay host-side. Watching from the view goes through the same control-plane watch as `github_pr_watch`.
- The thread sidebar's Files tab shows the thread's files: a Recent list of files outside the repositories changed since the thread started (repository changes are the Diff tab), each checkout's tree, the workspace outside its checkouts, and the agent's home (`/home/agent`, where desktop apps save). Each section folds away from its title, and the browser remembers which are folded (per repository name, across threads). A filter narrows every list. `GET /api/tasks/:id/files` (owner only) lists every checkout's files on disk that its `.gitignore` files do not ignore, plus files committed at its HEAD even when an ignore rule matches them, using host git against the checkout's shadow (`ls-files --others` against an empty index, and `ls-tree` of the HEAD commit read from the checkout's files), so nothing in the agent-writable `.git` runs. The workspace and home are walked for regular files with size and modification time; symlinks are neither listed nor followed, and each directory is read through an open descriptor whose real path must still be inside the folder (`/proc/self/fd` on Linux), so swapping a directory for a symlink cannot list anything outside it. Dot names, `node_modules` and `__pycache__` are hidden unless `?hidden=1`. Each list holds at most `MAX_CHECKOUT_FILES` (20,000) with `truncated` set past that. Any listed file downloads with `GET /api/tasks/:id/files/download?root=workspace|home|checkout&checkout=<id>&path=` (owner only) as `application/octet-stream`, `Content-Disposition: attachment`, `Content-Security-Policy: sandbox`, exactly the `Content-Length` the file had when opened (a file still being written is cut there; one that shrank ends short and the download fails). The box opens the path without following a final symlink or blocking on a named pipe, and serves it only if it is a regular file whose real path, checked after the open, is inside the folder and is the same inode; a checkout's files resolve under the workspace, so a checkout directory swapped for a symlink cannot lead out. The legacy relay answers 413 to any response over `MAX_RELAY_RESPONSE_BYTES` (20 MiB), since a relay frame carries the body base64-encoded and Cloudflare refuses WebSocket messages over 32 MiB. The app sends a `HEAD` of the same URL before handing it to the browser, so a refusal (413 through the relay, 404 for a file gone since the listing) shows in the panel instead of being saved as a file or replacing the page. The app refetches the lists on the same run events as the diff, only while the tab is open.
- `repo_checkout` and the GitHub tools (`git_push`, `github_pr_create`, `github_pr_status`, `github_pr_review`, `github_pr_update`, `github_pr_comment`, `github_pr_reviewers`, `github_pr_labels`, `evidence_attach_to_pr`) run on the box host, not in the sandbox; the GitHub tools name the checkout they act on (optional when the thread has one). A thread owns as many pull requests as it needs: `Task.pullRequests` records every one it opened, took over with a checkout, or watches, each with the checkout whose pushes update it. `github_pr_status` takes the pull request number, and the other pull request tools default to the checkout's own pull request when no `number` is given. Merging and approving are not offered to agents. `evidence_attach_to_pr` captures the running desktop, commits the PNG to a per-pull-request `kestrel-evidence/pr-<number>` branch through the Contents API, and comments a `?raw=true` markdown image with its caption; it never writes the pull request's head or base branch. The host pushes with the owner's GitHub token passed only through git's per-process config, and the PR calls use the same token from the host side. Mirror fetches for a checkout (base branch or pull request head) work the same way. The token never enters the sandbox environment, tool arguments, tool output, or logs. Pushes never force. `git_push` and `github_pr_create` can explicitly name a local branch shared with a linked worktree; they refuse the checkout's base and the remote's default branch. A PR for another branch is still the thread's to manage, but it is not the checkout's own pull request, so later PR operations should name its number.
- Agent runs also get a `gh` on `PATH` (`gh/*`): a bash script the harness writes to the task home's `.kestrel/gh` for every run, ahead of everything else on `PATH`. It holds no GitHub credential. It sends its arguments, working directory and the files the command reads (`--body-file` for `gh pr`, `--input` and `-F key=@file` for `gh api`; read inside the sandbox, `-` is stdin) to `POST /gh/:taskId` with the run's token, and the box runs the command with the owner's token on the host and replies with its stdout, stderr and exit code. It reproduces GitHub CLI 2.87.3 with stdout not a terminal (flags, validation, messages, output bytes, `--json` and `--jq`, exit codes) for `gh api` and `gh pr checks`, `close`, `comment`, `create`, `diff`, `edit`, `list`, `ready`, `reopen`, `review`, `status` and `view`; usage and help texts in `gh/usage.ts` are captured from the real CLI. Every `gh pr` command works only on the thread's GitHub checkouts (`-R`, URLs and `--search` cannot reach other repositories), opens pull requests only from the checkout's branch, and refuses what the GitHub tools refuse (approving, merging); browser, editor, assignee, project and milestone options say they are unavailable. `GitHub.api` decides what `gh api` sends (`github/api-policy.ts`). Reads go anywhere on the API, not only to the thread's checkouts (as `repo_checkout` can check out any repository the owner can read): GET and HEAD without a body, and GraphQL queries (parsed with graphql-js). Writes are an allowlist, only on repositories checked out in the thread, with a JSON body limited to the listed fields and no query string: create an issue (`title`, `body`, `labels`), edit one (`title`, `body`, `state`, `state_reason`, `labels`; issue numbers include pull requests, as `gh pr close` does), comment on one, add or remove its labels, reply to a pull request review comment, re-run an Actions run, its failed jobs or one job, and the GraphQL mutations `resolveReviewThread` and `unresolveReviewThread`, whose threads (literal or from variables) are looked up first and must belong to a checkout's repository. Anything else (merging, approving, assignees, contents, refs, settings, other mutations) is refused before any request, as are method-override headers; writes follow no redirects. It calls only the configured API, following read redirects off it without the token. `{owner}`, `{repo}` and `{branch}` come from the working directory's checkout; `--template`, `--verbose` and other hosts say they are unavailable, and response bodies are text. Other `gh` commands say what is supported and exit 1. `--jq` runs jq 1.8 (WebAssembly) on a worker thread that is stopped after 10 s; the compiled box binary builds that worker in (`scripts/build-box.ts`).
- Agents manage automations with the `automation_list`, `automation_create`, `automation_update` and `automation_delete` MCP tools. The box calls the control plane at `/box/automations` over HTTPS with its box token and the thread's owner in `x-kestrel-box-user` (`BOX_USER_HEADER`, from `packages/protocol`). On a managed box it authenticates with its own secret and sends its id in `x-kestrel-box-id` (`BOX_ID_HEADER`) instead. The control plane checks the auth and that the user exists and, for a managed box, that the user is assigned to it, then runs the same handlers as the browser. A tool sees and changes the automations of its thread's owner.
- Each thread's agent can start another thread with `thread_spawn`, optionally checking out a repository before sending its first task. The new thread has its own workspace and conversation. Agents can also reach the owner's other threads with `thread_list` (active threads, archived ones left out), `thread_read` (a thread's latest messages) and `thread_send`. A sent message is stored on the target thread as a user message with `fromThread` (the sending thread's id and title) and shown there as coming from that agent. It joins the target's running run (the running turn takes it at once; once the run's last turn is over it waits in the run's `task_inbox`), or starts a run that resumes the target's latest session (on that provider's default model); it never answers the target's open `task_ask` question, and an archived target refuses it with 409. The receiving agent reads who sent it and to answer with `thread_send` only when asked for something, so two agents do not keep waking each other. Everything stays on the box: another user's thread is NotFound, like on every owned route.
- `delegate_task` starts tracked work in a separate thread, while `thread_spawn` starts an independent thread. The child stores the parent thread, initiating run, retry key and original run; `delegation_status`, `delegation_wait`, and `delegation_cancel` refer to that original work. The parent sees its children in chat. `delegate_batch` prevalidates and dispatches up to ten tasks with shared context; a partial failure leaves prior children in place, and repeating the same key resumes the batch. A request key is scoped to the parent thread: a later run repeating it (after a usage-limit resume, a retry or a restart) gets the existing child back, and it cannot be reused with different inputs. A run inherits the parent's selected model when known, otherwise the box default, and the box's existing run queue limits concurrency. A blocked delegation wait lends its parent's slot to queued work, reacquiring it before the tool returns. Delegation depth is limited to four.
- Child results are delivered to the parent automatically, including after the parent run ends; completion waits for nested work and its result-driven continuations. A wait that takes the result first acknowledges it and suppresses automatic delivery; status remains readable. A stable message id and persisted acknowledgement suppress duplicate delivery during normal operation. When a parent run containing a notification is interrupted by a box restart, delivery is retried in a fresh run with a restart notice: this is at-least-once, since the old run may already have seen the result. Cancellation stops the delegated run and its descendant runs, preserving their threads. A child needing input causes a wait to return and notifies the parent; its question remains for the user to answer in the child thread. A child that only reported needs input, with no question pending, ends with its run so its result goes up. Result summaries are bounded in automatic messages; the full thread remains readable. Per-run usage is reported when the harness provides it. If the box restarts before dispatch, the child is marked failed rather than silently creating a second thread; in-flight runs are reconciled as failed as usual.
- Usage limits do not end delegated work. A child whose run failed on a provider usage limit is held while the box checks the reset and, once armed to resume (`Task.usageLimitResume` with auto-resume on), until it resumes: no result goes up, `delegation_wait` keeps waiting and status names the reset. The run that continues it, the automatic resume or the user handing it to another model in its thread, becomes the delegated run, and its result is the one delivered. "Return to parent now" (the child's usage-limit notice, or the parent's strip) drops the arm and delivers the failed run's result at once; turning auto-resume off does the same, and once that result has gone up the box refuses to turn auto-resume back on (the parent could never get the resumed run's result; a message to the child still continues its own thread). A parent stopped by a usage limit queues its children's results and questions until it resumes or the user's next message starts a run, instead of starting a run per notification that fails on the same limit.
- Delegation assignments and automatic result/question notifications have distinct framing from ordinary peer mail. Children give their final response in their own thread rather than also sending it with `thread_send`; automatic notifications do not invite replies or answers to the user's questions.
- A delegation may supply a JSON Schema for its final response. Kestrel includes it in the assignment and validates the returned JSON; the status and notification report validation failures without hiding the original response. Role names are prompt guidance, not separate permission profiles. Children use their own thread workspace and may check out a repo, branch or PR; local uncommitted files and the parent's transcript are not copied.
- An agent can call `thread_close` as its final action when its finished work needs no user attention, such as an automation check that found no issues. It archives its own thread — and any threads it spawned or delegated — and ends its run.
- Archiving a thread (`POST /api/tasks/:id/archive`; `DELETE` lifts it) tears down its runtime: running runs are cancelled, the desktop stops, and the sandbox network and systemd slice are removed. A thread's sub-threads — threads it spawned with `thread_spawn` or delegated work to with `delegate_task`, transitively — archive with it, each runtime torn down the same way. The workspace, checkouts, branches, messages and runs stay, and the threads leave the active list. While archived, sending a message or starting the desktop fails with 409 Conflict. Unarchiving lifts only the named thread and starts nothing on its own.
- Hovering an agent reply in the transcript (always shown on touch screens) offers Copy (the reply's Markdown) and Fork, after t3code's assistant message actions; both appear once the reply's run has ended. Forking (`POST /api/tasks/:id/fork` with an agent `messageId`) creates `<title> fork` on the same box holding copies of the thread's messages up to and including that reply, attachments copied to new files, followed by a "Forked from" system note. Runs, run items, native sessions and the workspace are not copied: the fork's first run starts a fresh session with the copied conversation as its handoff, and the fork's `pickedRepo` is the source's picked repository or first checkout, so its agent checks the repository out again.
- Kestrel's own managed and relayed boxes count failed tools and agent turns for operators at `GET /api/fleet/tool-failures?days=`. Agent failures include a scrubbed diagnostic when available, plus the exit code or signal. Tool and agent failures use scrubbed error signatures (`core/tool-failures.ts`); oversized outputs use a fixed signature, and scrubbing is heuristic so other signatures may still be sensitive. Declined actions, stopped runs and replays are skipped. Reports are best effort, at most once a minute, and kept per UTC day for 90 days without a user, thread or box. User-owned boxes do not report unless configured with the shared relay token.
- Desktop video, audio and input are always WebRTC, signaled over the authenticated desktop WebSocket, direct or through the legacy relay. There is no WebSocket media path and no opt-in. See [box.md](box.md#webrtc-desktop).
